# 设计探索与交付

按已选模式读取适用小节。完整六版与获奖打磨仅用户明确要求时启用；C仍是甲/乙/丙三方向。本文件保存v29详细方法，执行顺序以制作流程为准。

## 2. 完整流程（只执行本次范围内适用的步骤；完整探索时按顺序进行）

**模式F边界**：本节网站设计/制作流程不用于默认仅提示词的任务；模式F按专用调用流程、角色和模板完成交付。

### 步骤1 明确目标与约束
写出：目标用户、用户来这里要完成的事、核心转化动作（只能一个主动作）、品牌调性（3 个形容词 + 3 个“不要像”）、硬约束（技术栈、已有设计系统、内容是否已有、截止时间）。
- 出口检查：能用一句话说出“谁，在什么情境，来做什么，我们希望他点哪个按钮”。说不出就不往下走。

### 步骤2 拆解（模式B 拆参考站）
制作任务先完成[五站调研](五站调研与记忆点.md)，再由C构思三个原创主基调与可视预览，或由D展示参考候选供选择。模式B继续深入拆解指定参考站；不把每个调研案例都扩成完整拆解。C区分案例观察和本项目原创决策，不编造“参考站证据”。

按 `references/拆解方法.md` 的六层逐层做，每层都写“是什么 + 为什么”。工具用法见 `references/工具清单.md`：优先用 Chrome DevTools MCP 截图取证、dembrandt 提取令牌；没装 MCP 时用 `scripts/` 兜底。拆解视觉层时，用 `references/方法论库.md` 的 Gestalt、NN/g 视觉层级、Material 断点五问做判断依据。
- 先取证再判断：截图（375 / 768 / 1440 全页）、实测字体颜色间距、素材与实际动画播放。Lighthouse/axe留在用户明确要求的工程检查，不进入美学评分。没有实测数据的结论要标“推断”。
- 出口检查：每层至少 3 条观察，每条都有“为什么”；“为什么”不能是“因为好看”。

### 步骤3 提炼并适配为项目DESIGN.md
将调研所得适用原则改写为目标项目的设计规则；原创每个方向先说明核心记忆点、产品关系、用户感受及实现方式，选定后记录到DESIGN.md。模式A保留指定参考的特色和锁定规格，不强制另创风格。文档按[五站调研与记忆点](五站调研与记忆点.md)中的Google格式衔接，区分实测、推断和原创决策。
- 原则写成可执行判断句，附证据和迁移取舍，不只写“简洁”或“像参考站一样”。
- 核心记忆点须能用具体的一句话复述，说明渲染技术、素材与动效驱动如何做成该体验，并在预览及代表性内容/状态中体现；不以换色、叠特效或随机种子代替概念。
- DESIGN.md作为实现和同次评审依据，原则无需再独立复制成另一份报告；只分析时交付本次范围内的文档与观察，不越界制作。

**以下六版流程的适用边界**：步骤4、5、7及“第1～3版不交付、不选中”的编号规则用于完整六版探索，不用于模式C 的三方向选择。C 以甲/乙/丙命名三个可选主基调，三者都须展示预览且都可被选中；用户选定后只实现该方向，再按适用要求验证和评审。不得额外强制六版或把用户的选择判作不可交付的基线。模式D转A后沿用研究证据，默认直接制作一套；用户选择先比较时，按统一提示词做三个同主题、同主参考的独立预览。A/C可选预览不套用六版中的不可选基线，不满意时按反馈继续。

### 步骤4 大众基线 1～3 版（不交付）
快速写出第一时间想到的方案，每版一张方案卡（见下方“方案卡格式”）。
- 目的只有一个：把套路摆上桌。每版最后写“套路清单”：用 `references/反套路清单.md` 的编号点名这一版用了哪些行业惯例和 AI 惯性（例如 C1 居中大标题+双按钮+渐变、C2 三列图标卡片、A10 每段淡入上滑、B6 单一色相）。
- 仅在用户明确要求完整六版探索时，与4～6版合并交给一次方案卡对比，不逐版评分循环；1～3版只作基线，不能被选中。

### 步骤5 发散4～6版（仅明确要求完整六版探索时）
- 每版换一个发散方向，三版方向不能相同。可选方向：
  - 换隐喻（把网站当成：一本杂志 / 一张票据 / 一个控制台 / 一本日志 / 一张地图 / 一个展柜……）
  - 换信息组织方式（按时间 / 按问题 / 按人 / 按场景 / 按数据，而非按“功能模块”）
  - 换视觉风格（编辑排版型 / 极简数据型 / 实物摄影型 / 纯文字型……）
  - 换核心交互（滚动叙事 / 一个可操作的小工具 / 对比切换 / 筛选器即首屏……）
- 每版必须写“这一版刻意避开了基线的什么”，至少点名 2 条基线套路（用 `references/反套路清单.md` 编号）。
- 导航栏滚动行为、开场动画、页面切换、Shopify Editions 式的“浮动卡片 + 透明物件”趣味交互：先用 `extract-motion.mjs` 看参考站 / 获奖站怎么做（`navOnScroll`、`animations`），写法见 `references/交互动效.md` 末节。
- 可以用 Canvas / WebGL / Three.js 做核心想法，但先过 `references/特殊渲染.md` 第 1 节三问；整站最多一处。
- 每版至少用一项 `references/前卫设计与前端技巧.md` 里的平台能力或趋势方向来实现核心想法，并写明它怎么服务目标；引入趋势前先过该文件里的 Smashing 五问。
- 发散的方法依据：Crazy 8's（先出量、压住评判）、Double Diamond 的 Develop（同一问题多个解法、跨领域找灵感）、IDEO “How might we…” 提问、Kano 兴奋型需求（见 `references/方法论库.md`）。
- 发散方法参考 Google Design Sprint 的 Crazy 8’s：先快速出量，压住内心的评判，第一个想法往往最缺乏新意（见 `references/设计原则库.md` 第 E 节）。
- 出口检查：把 4～6 版和 1～3 版放在一起，外行也能一眼看出不是同一个方案的微调。

### 步骤6 独立主审与一次定向复核

默认只对选定并实际制作的版本执行：主Agent完成并自查 → 独立首审 → 一批集中修改 → 按需独立复核。最多两次真实调用，首审达标就止；不因引用unslop或GSAP另加评审Agent。先按[自动化与门槛](自动化与门槛.md)登记、生成统一审查包和回收结果，宿主与exec共用预算。没有实际调用不能填Agent ID或冒充独立评分。

- 首审全量盲评，不给历史分、自评分或辩护。看目标、参考、实际截图与播放证据，读取[评分表](../templates/评审评分表.md)、[unslop审查法](unslop-审查法.md)和反套路清单。
- 阻塞项可为0，建议最多5条，不凑三个致命问题。每项定位位置、证据、影响、修法和验收条件；保留已有优点。主Agent核对接受/部分接受/驳回，驳回须有确切引用。
- 复核换全新Agent，带冻结问题和新证据，明确标为定向复核而非盲评。仅以回退或视觉约束失败新增阻塞项，不重新发散已选方向。受影响维度独立给新分，其他维度继承首审；无法可靠限定范围就同次全量复核。主Agent不加分，脚本合成并标注各维来源。
- 沿用design-aesthetics-v1：构图25/底线20，排版20/16，色彩20/16，风格20/16，动效15/12；总分≥85。三项视觉约束为视觉完整性、禁用效果、动效表现；性能和工程指标不占分，不为这些指标删动画。A核对当前参考一致性，不要求连续两轮。
- 每批记录changes.md及问题处理，检查真实交互。首审与最终版本保留375/768/1440截图；影响范围外的专项检查有依据才继承，不把未重跑写成通过。静态图不能证明动效/hover全程，动效证据按实际关键时刻采集，不每章固定截帧。汇总报告在收尾生成一次，不逐条改动重建。
- 两次后仍不达标/未验证，按真实状态closed-unmet/closed-unverified收尾，报告当前版本和遗留项；不无限追分、不靠等待用户确认结束。评审后又改动须标证据过期，不能自动开第3次。用户明确要求继续时再记录一次追加额度。
- 只有用户确实要求完整六版探索时，方案卡合并一次对比；只选中的成品走上述两次流程，总上限3次。默认不启动完整六版，不再让4～6版各自循环到达标。

### 步骤7 选定最终版
- 只从 4～6 版里选，可以组合多版优点，组合选定后只制作一个最终版，纳入同一成品两次评审预算，不另追加组合版循环。
- 输出方案对比，以及已选成品的真实评分、调用次数、达标状态和选择理由（3条以内）。

### 步骤7.5 获奖级打磨（仅用户明确要求）

按[获奖级品质标准](获奖级品质标准.md)选取真实对标证据，仍只评视觉。该专项额外最多2次调用、1批修改：一次对标评审及按需一次复核；不再连续两轮无高/中项才停。普通制作加此专项总上限4次；再加明确要求的完整六版探索，总上限5次。begin时登记专项预算，不因主文件存在本节自动启用。

八维对标用于说明差距，五维评分仍须达标。到限仍有差距就如实报告，不暗中续轮、不以资源成本删动画。只能说“按公开标准自检并对标了哪些网站”，不能宣称获奖或自动达到获奖水准。

### 步骤7.8 文案最终对账（生成与独立审核前置于页面定稿）
网页制作的 Gemini → 独立文案审核在上面的执行顺序第3步完成，不能拖到完成页面后才决定是否调用。细节见 [文案审核](文案审核.md) 第3.5节。
- 主 Agent 只整理事实、块用途和长度；Gemini 提供候选；审核员仅挑选和保留原意的小改。全数淘汰时带原因交回同一入口，不由主 Agent 或审核员另写替代稿。
- 审核产物保留每个块的确切 `from: 文件#块id#从0开始的候选序号` 和实际审核代理 ID。原始回执与正文一致性只能提供可追溯证据，不能独立证明服务商的上游模型身份。
- 最终对照实际页面的初始、hover、展开、错误、成功及移动状态；标题的嵌套 span 和 CSS 伪元素也不能偷偷带句号。`check-copy --style-only --url ...` 可单独检查标点，不能替代来源与审核验证。
- 无新增事实，按钮含动作，长度符合版式；40%～60%的压缩比只适用于确有冗余的长草稿，不给本来简短合格的候选强行减半。

### 步骤8 输出设计说明 + 实现说明
- 设计说明：最终版的原则清单、页面结构（逐区块：目的 / 内容 / 主视觉 / 交互）、设计令牌草案（颜色用 oklch 定 4～6 个基础令牌再派生；字号阶梯，营销/编辑页可用 Utopia 式 clamp；间距阶梯、圆角、阴影、动效时长），令牌建议按 W3C DTCG 格式输出、各状态（hover / focus / active / disabled / loading / empty / error）。
- 实现说明（给 AI 开发）：技术栈及核心场景的渲染/资源/驱动/合成方案与验收依据、组件拆分清单（先查项目已有组件、动效预设、设计令牌，能复用就复用或加 variant）、每个区块的验收标准、响应式断点（375 / 768 / 1440）、可访问性要求（WCAG 2.2 AA：对比度、焦点不被遮挡、点击目标 ≥ 24×24 px、键盘可达、`prefers-reduced-motion`）、工程性能要求（仅用户明确要求后期优化时制定，不作为当前设计评分或删减动画的理由）、浏览器支持策略（核心布局只用 Baseline 广泛/新近可用的特性，有限支持的特性用 `@supports` 做渐进增强）、验证方式（当前阶段以截图、实际播放和必要功能检查为准；Lighthouse仅用户要求工程优化时运行）。
- 写清楚哪些是推断、哪些还没验证。

## 3. 方案卡格式（每一版都用）

```
### 第N版：〔一句话名字〕  〔大众基线 / 发散〕
- 发散方向：〔隐喻 / 信息组织 / 视觉风格 / 核心交互〕（基线版写“无”）
- 核心想法：一句话
- 核心记忆点：记住什么 / 为什么属于这个产品 / 怎样感受并贯穿 / 实现与触屏适配
- 首屏：放什么、主动作是什么、第一眼看到什么
- 页面结构：区块1 → 区块2 → …（每块一句话目的）
- 视觉：字体方向、色彩方向、图像方向
- 关键交互：1～2 个
- 表现技术：核心场景 / 渲染接口与库 / 素材形态 / 驱动与合成 / 如何验证；已有实现如何复用
- 刻意避开的基线套路：（发散版必填，至少 2 条）
- 套路清单：（基线版必填）
```
