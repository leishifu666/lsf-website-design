# 内置参考取证与组件规格

模式A使用本文件、[风格还原](风格还原.md)、本技能scripts和[组件规格模板](../templates/组件还原规格模板.md)即可执行参考取证，不需要安装另一个网站克隆技能。只分析或仅反推提示词时取本次需要的方法，不启动实现或评审。

取自 `lsf-clone-website` 的执行顺序是**浏览器遍历 → 找到原资源和每层职责 → 实测控件多态 → 写好对应组件规格 → 同态对照**。A 把克隆里的原文和品牌素材换成目标主题，保留参考的构图、操作与资源关系。原站清单、实际文件格式、漏看章节的恢复步骤和可见边框判断见 [A 模式证据格式](A模式证据格式.md)。
## 1. 确定边界与工具

- 沿用用户指定URL、主题、页面范围、原项目技术栈和已确认要求。侦察指定入口可达的站内页、章节、模板、弹层和返回路径；识别后按用户任务裁定制作范围。相同模板可归并实例，外站留边界，多个参考隔离证据。
- 指定主参考时先执行[原站侦察与回放](原站侦察与回放.md)，拿到真实拓扑与输入记录。其他参考按需补内容，不参与决定主参考的前景、镜头与交接方式。
- 使用当前可用的浏览器自动化查看渲染结果、操作和计算样式；本技能scripts可辅助。没有某个MCP或Next.js脚手架不构成缺项，不要求用户另装技能。所有浏览能力不可用时保留已有证据，如实说明缺口，不猜精确参数或把截图当交互证据。
- 在原项目工作；先看已有组件、样式、动效、素材和构建命令。不开worktree、不自动提交，不把某一框架或tsc命令强加给其他项目。

## 2. 页面地图与全局基础

在现有拆解报告或ref记录中列一张页面地图：

| 区块ID / 顺序 | 内容与素材 | 布局 / 覆盖层 | 交互驱动 | 依赖 / 响应式差异 |
|---|---|---|---|---|
| 实际区块 | 文字、主体、背景等角色 | 流式、sticky/fixed、滚动容器、z-index和遮挡关系 | 静态、滚动、点击、悬停、时间或混合 | 共享舞台、导航、其他区块、375/768/1440变化 |

先核实字体角色与可用字体文件、颜色、间距、主容器、断点、全局滚动方式和共享素材；全局基础先稳定，再制作依赖它的组件。只复用用户自己的或获授权资产；参考站图片、字体、Logo等按[氛围图片](氛围图片.md)和任务授权处理，不能默认复制上线。

DESIGN.md说明整体设计语言；reference-spec.json承载锁定值并生成令牌；组件规格描述局部结构、状态和素材映射，优先引用令牌。证据冲突时回到实测核对，不维护互相矛盾的三套数值。

## 3. 扫描交互与状态

先慢滚完整页面，在代表区块停留，观察导航、固定区间、自动切换、进度、场景和主题变化；再用点击、悬停、键盘及适用的触屏操作确认机制，并检查反向滚动、重复触发、关闭与恢复。操作以任务范围内的展示状态为限，不因扫描去提交订单、发送消息或改变真实业务数据。

每个有状态的组件先填清：

**驱动输入 → 触发条件 → 初始状态 → 变化过程 → 目标状态 → 退出/反向/打断后的结果**

- 把“停住不滚也会变化”与“随滚动进度变化”分开；点击和时间共同控制时记录混合驱动。不能看到侧栏高亮就默认写成点击tab。
- 逐一查看本页面范围内的tab、轮播项、菜单、弹层、折叠项和有区别的组件变体，记录每个状态的文字、图片及布局，不只记录默认态。
- 交互内容相同、样式相同的重复控件可复用规格；各状态覆盖清单须能看出哪些已观察、哪些不适用、哪些未验证，不以抽样结果代替全覆盖。
- 375/768/1440检查列数、顺序、固定关系、素材裁切与输入方式；只知道两个宽度表现不同，不能虚构精确断点。
- 导航记录顶部、下滚、停滚、上滚和返回顶部；滚动场景记录进入、过程中、离开、倒滚和锚点跳转。复杂叙事再读[滚动叙事](滚动叙事.md)。

## 4. 测量样式与素材层

已有extract-tokens、extract-components、extract-motion、extract-media和check-transitions用于发现线索、抽样与输出草稿，不会自动写完组件合同或保证穷尽所有状态。按页面地图和状态清单补取证，不重复测已有可靠证据。

对代表元素在对应视口/状态读取getComputedStyle和getBoundingClientRect：字体、行高、字距、颜色、尺寸/容器关系、边距、grid/flex、边框、圆角、阴影、定位、透明度、transform、遮罩、混合和过渡。重要伪元素与子元素单独检查。

- 前后状态都保留对结果有影响的值，包括0、none、auto及透明色等重置值；不能为了压缩输出删掉状态差异。
- 深层树或大量子项若被工具截断，在证据中标截断范围并补查关键部分；没有遍历到不等于不存在。
- 区分声明值、当前计算结果和视口相关尺寸；只测出某宽度下的px结果，不代表应在所有宽度写死该尺寸。
- 精确时长、缓动、Observer阈值和库配置须有可读取的声明或运行时证据。computed style或录屏只能支持部分结论；估算记录采样条件和范围，无法确定内部机制则标推断/未验证。
- 逐层枚举img/picture、背景图、伪元素、叠层SVG、video、Canvas/WebGL与适用的模型资源。记录当前实际图片currentSrc、视口、自然尺寸与显示尺寸、透明度、裁切、锚点和遮挡；图片src不能代替响应式资源核对。
- 判断画面来自真实UI、视频、Lottie、Canvas或实时场景，不能把视频中的界面误拆成大量HTML控件。素材不存在DOM图片节点时，继续检查实际渲染来源并标明能力边界。
- 为本项目映射自己的照片、透明物件、模型和预渲染素材；一张合成图拟议拆层时标为适配方案，不虚构原站已有独立图层。

### 4.1 核心场景的渲染技术与公开源码取证

此项属于实施前的现有取证，不另加方案或评分轮次。用户2026-10-31明确要求查清参考使用的技术和代码，不能只凭画面把三维场景替换为背景图位移。

1. 分层辨认：页面/路由框架（例如React/Remix）、交互与时间线（例如GSAP/Theatre/Rive）、场景库（例如Three.js/R3F）、渲染接口（Canvas2D/WebGL/WebGL2/WebGPU）、资源（图片/视频/深度图/GLB/GLTF/KTX2/shader）。它们不是互斥选项；canvas只是载体，看到它不能判定2D或3D。
2. 从实际页面脚本、modulepreload和网络资源找相关入口，获取公开发布bundle，追踪场景、相机、loader、渲染循环、材质与转场模块。保留实际URL、时间、hash及相关代码位置。压缩代码可格式化阅读，不能把格式化结果称为作者原始源码。
3. 如bundle声明sourceMappingURL或SourceMap响应头，尝试对应公开map；可取得时阅读sources/sourcesContent，不可取得时记录状态，不无限猜路径。区分公开构建代码、公开仓库、完整私有源码与原始建模文件；不能假称获取了后两者。
4. 用真实运行证据交叉核对：上下文创建、实际资源请求、模型元数据/mesh/骨骼/animation、时间线配置及进度更新。框架字符串只在依赖中出现不证明某区块使用它；能力探测创建的WebGL上下文也不能全部当作主场景实例。
5. 建模来源需要额外证据：GLB证明加载模型，但不能据此断言模型由Blender、AI或深度图生成。作者/团队公开说明可作为来源并与文件结构交叉核对；没证据就保留未知。技术问题优先引用原站公开代码、库官方资料或作者原文。
6. **锁定并沿用实现机制**：把“视觉对象→实现代码→资源→触发/进度→本项目实现”写入现有ref记录及组件合同；锁定核心渲染接口、场景库、资源形态、驱动和合成方式后再实施。参考用Three.js/R3F与WebGL模型，就实现对应实时场景；参考用深度图位移、骨骼动画、shader转场或Rive状态机，就实现对应机制。不能擅自改为图片位移、预渲染视频、通用fade-up或另一套效果后仅记录差异便视作完成。
7. **分清技术层与适配范围**：页面/路由框架与场景渲染层分别核对；在现有项目容纳同一核心机制，不为模仿页面外壳而重建项目，也不以已有框架或熟悉GSAP为由取消原机制。GSAP可编排外围或驱动适合的属性，不能强制替换参考核心时间线/状态机；一个属性须有明确控制者。新主题可换成自己的模型、纹理、文案和品牌，仍需保留相应几何、材质、空间、控制和转场关系。
8. **机制验收不能只看外观**：核对实际代码路径、加载资源、渲染输出、进度/状态更新和关键中间帧；模型文件存在、依赖已安装或静态图相似均不够。能力不足、源码不全或明确技术约束冲突时，指出对应缺口并继续独立部分；不能单方面降级。只有用户明确改变还原目标才采用不同机制，并记录新范围；正常模式与备用静帧分开验收，未实现原机制不得称为同机制还原完成。公开构建代码足以确认机制时，不把拿不到完整私有工程当作无法开始的理由。
7. 公开可读不等于获准复制上线。参考代码和模型可用于取证；网站实际素材与实现继续遵守用户授权和各自许可。

## 5. 组件开工前的规格

重要区块、有状态组件及其独立变体在实现前按[模板](../templates/组件还原规格模板.md)写好规格。简单重复控件共享同一份规格，不机械地每个按钮建文件；已有components.md可直接补充，复杂组件再保存为ref/components/<组件名>.spec.md。

实施所需的结构、核心状态、素材关系或锁定值缺失时先补取证，暂缓依赖它的组件，继续无依赖工作。确实不可观测的细节标清缺口及拟议实现，不伪称参考事实；会改变核心风格或目标的适配才澄清。

每份规格包含：目标文件与依赖、实际证据、结构与令牌引用、交互驱动、状态/内容转换、素材层、三档布局、用户要求的适配、可观察验收条件。静态组件可写无状态，但须确认是否有链接或hover行为。

## 6. 多构建Agent：共享基础先行，按所有权并行

用户2026-11-02最新明确：选择只做一套时，由当前对话主Agent直接制作，不因2026-10-31的历史多构建授权自动派出构建Agent。以下组件并行方法仅在用户本次另行明确要求实现并行时采用；三预览的独立构建则按[预览分流](三方向预览与确认.md)执行，同一设计提示词与文件隔离规则保持一致。独立文案审核与视觉评审职责继续保留，不按卡片数或规格行数机械增加Agent。

1. 主Agent负责原项目定位、全局令牌/字体、共享组件与类型、资源路径和页面装配。只有这些依赖稳定，相关组件才并行；共用一个渲染舞台或强耦合状态的部分由一个负责人处理。
2. 每个构建Agent获得明确文件所有权、组件规格正文、截图/状态证据路径、可复用组件、素材、接口和验收条件。明确告知“你并非独自在代码库工作，不回退他人修改，只改分配文件；需要更改共享基础先交主Agent处理”。
3. 所有Agent共享原项目目录；共享样式、依赖清单、锁文件、入口和路由由主Agent统一修改，其他Agent不同时写同一文件。不创建worktree，不用分支合并充当回收步骤，不复制出另一个项目。
4. 主Agent可在构建Agent实施已完成规格的组件时继续取证下一个区块；缺规格不得提前派发，跨组件依赖不得靠猜。并发数量服从宿主实际能力。
5. 构建Agent回报实际改动文件、完成状态、相关检查与未验证项；类型/构建命令按项目配置选用。主Agent核对接口、整合和联动，再对完整页面运行适用检查；检查失败先修复，不能把“Agent说完成”当作集成完成。

这是实现并行，不是新增独立评分环节。文案继续Gemini生成、独立审核；构建Agent不自称独立评审员，成品仍最多2次真实设计评审、1批集中修改。

## 7. 同条件自查与评审交接

参考与实现采用相同视口、滚动位置、tab/展开状态和可比的动画阶段，逐区块核对构图、字体、素材层及真实交互；先查规格是否测错，再查实现是否偏离，记录证据与目标项目适配。

在现有评审目标卡（prepare-review的--target）中写明A目标、规格版本、重要组件合同路径、参考证据和观察限制；可消费的关键合同/状态摘要直接放入目标卡，截图与动效证据进入原审查包。评审者若不能读取路径，补入对应正文和图片，不只发网址或本机文件名，按当前审查包的 style_fidelity 字段逐项返回独立结论。

将机制合同、状态覆盖、素材完整性、同条件对照并入主Agent自查和现有首审。核心机制对照实际代码、资源、运行更新与中间帧；已测值与估算分开，证据不足列缺口，不能用只截默认态或“构建通过”证明还原完成。复核仍只核原问题及实际影响，不重新发散或增加第三次评审。
